# ТИШКА — сайт с тестами на футболку

Простой сайт на Go: страница с ценностным предложением → выбор теста →
прохождение теста → своя футболка на выходе (картинка генерируется
на лету по результату теста).

Без фреймворков и без сборщиков фронтенда: чистый Go (stdlib) на бэкенде,
vanilla HTML/CSS/JS на фронте. Внешних зависимостей в `go.mod` нет — сайт
собирается одной командой `go build`, без доступа в интернет.

## Быстрый старт

Нужен только установленный Go (1.22 или новее — используется современный
роутинг `net/http`, `GET /tests/{slug}` и т.п.).

```bash
# 1. Перейти в папку проекта
cd tishka

# 2. Запустить сервер (данные тестов и шаблоны сервер найдёт сам,
#    если запускать команду из корня проекта)
go run ./cmd/server
```

Откройте http://localhost:8080 — сайт готов.

Чтобы собрать бинарник (например, для деплоя на сервер):

```bash
go build -o tishka-server ./cmd/server
./tishka-server
```

### Проверить, что всё работает

```bash
go build ./...   # компилируется без ошибок
go vet ./...     # без предупреждений
go test ./...    # юнит-тесты движка подсчёта результата
```

## Настройка через переменные окружения

Все переменные опциональны — без единой из них сервер стартует с
разумными дефолтами (порт 8080, папки `data/tests`, `web/templates`,
`web/static` относительно текущей директории).

| Переменная      | По умолчанию     | Что делает                                   |
|------------------|-----------------|-----------------------------------------------|
| `PORT`           | `8080`          | Порт, на котором слушает сервер                |
| `TESTS_DIR`      | `data/tests`    | Папка с JSON-файлами тестов                    |
| `TEMPLATES_DIR`  | `web/templates` | Папка с HTML-шаблонами                         |
| `STATIC_DIR`     | `web/static`    | Папка со статикой (css/js)                     |
| `BRAND_NAME`     | `ТИШКА`         | Название бренда — подставляется в шапку/футер  |

Пример запуска на другом порту:

```bash
PORT=3000 go run ./cmd/server
```

## Структура проекта

```
cmd/server/            — точка входа (main.go), только сборка зависимостей и запуск
internal/
  config/               — чтение настроек из ENV
  models/                — доменные типы: Test, Question, Option, Result
                            + Validate() (проверка целостности теста)
                            + Public() (безопасная для браузера версия — без "ответов")
  store/                  — интерфейс Store + его JSON-реализация (JSONStore)
  quiz/                    — движок подсчёта результата по ответам (engine.go + тесты)
  shirtimg/                 — генератор SVG-картинки футболки по результату
  httpserver/               — HTTP: роутинг, обработчики страниц и JSON API
web/
  templates/                — HTML-шаблоны (layout + по одному файлу на страницу)
  static/                    — css и js, отдаются как есть
data/
  tests/                      — *.json файлы с тестами (см. "Как добавить тест" ниже)
```

Слои зависят друг от друга в одну сторону:

```
httpserver → quiz, store, shirtimg, models
store, quiz, shirtimg → models
```

`models` не зависит ни от чего внутри проекта — это "ядро" данных.
`store` спрятан за интерфейсом specifically для того, чтобы можно было
подменить JSON-файлы на базу данных, не трогая ни `httpserver`, ни `quiz`.

## Как устроен тест (формат JSON)

Каждый файл в `data/tests/*.json` — один тест. Пример упрощён, полные
примеры — `data/tests/vibe-check.json` и `data/tests/gift-mood.json`.

```json
{
  "slug": "vibe-check",
  "title": "Какой у тебя вайб сегодня?",
  "description": "Короткое описание для карточки в списке тестов",
  "emoji": "🌙",
  "questions": [
    {
      "id": "q1",
      "text": "Текст вопроса",
      "options": [
        { "id": "a", "text": "Вариант ответа", "tags": ["cozy"] },
        { "id": "b", "text": "Другой вариант", "tags": ["bold"] }
      ]
    }
  ],
  "results": [
    {
      "id": "cozy",
      "tag": "cozy",
      "name": "Название результата",
      "quote": "фраза, которая печатается на футболке",
      "description": "1-2 предложения, почему это подходит пользователю",
      "color_primary": "#8A9A5B",
      "color_accent": "#5C1A1A"
    }
  ]
}
```

**Как считается результат:** у каждого варианта ответа есть один или
несколько `tags`. После того как пользователь ответил на все вопросы,
сервер считает, какой тег встретился среди выбранных ответов чаще всего,
и показывает тот `result`, у которого `tag` совпадает с этим самым частым
тегом. При ничьей побеждает результат, объявленный раньше в массиве
`results` — так одинаковые ответы всегда дают одинаковый результат.

Логика в одном месте: `internal/quiz/engine.go`. Если захочется
усложнить алгоритм (взвешенные теги, несколько результатов сразу и т.п.) —
переписывать нужно только этот файл.

### Как добавить новый тест

1. Скопировать `data/tests/vibe-check.json` в `data/tests/мой-тест.json`.
2. Поменять `slug`, `title`, `description`, `emoji`.
3. Написать свои вопросы и варианты ответа, придумать свои теги.
4. На каждый использованный тег добавить ровно один `result` с таким же
   `tag`.
5. Перезапустить сервер — тест сразу появится в списке `/tests`.

Если что-то не сойдётся (например, для тега нет результата, или у
вопроса меньше двух вариантов ответа) — сервер откажется стартовать и
подробно напишет, в каком файле и что не так (см. `models.Test.Validate`
и `store.JSONStore.Load`). Так опечатка в JSON ловится сразу при
запуске, а не когда реальный пользователь дойдёт до последнего вопроса.

### Как добавить новую страницу

1. Создать `web/templates/моястраница.html` с блоком
   `{{define "content"}}...{{end}}` (см. любой существующий файл как
   пример).
2. Добавить строку в `pageTemplates` в `internal/httpserver/server.go`.
3. Написать обработчик в `internal/httpserver/handlers_pages.go` (или в
   новом файле, если хендлеров становится много) и зарегистрировать
   маршрут в `Server.Handler()` в `server.go`.

## Картинка футболки: как это устроено

На старте у нас нет реальных фото футболок — принты появятся позже, когда
дизайнер сформирует стиль. Поэтому картинка на странице результата не
файл, а SVG, который сервер рисует на лету (`internal/shirtimg`): берёт
`color_primary`, `color_accent` и `quote` из JSON результата и рисует
простой силуэт футболки с этой цитатой на груди.

Когда появятся настоящие принты — этот пакет можно перестать вызывать и
просто отдавать ссылку на настоящую картинку (например, положить файлы в
`web/static/shirts/` и отдавать их через уже существующий файл-сервер).
Хендлер `GET /shirt-image/{slug}/{resultID}` — единственное место,
которое нужно будет поменять; фронт и остальной бэкенд не заметят разницы,
потому что они работают с `image_url`, а не с тем, как эта картинка
получена.

## API

Помимо HTML-страниц сервер отдаёт небольшой JSON API — сегодня им
пользуется собственный фронт (данные теста уже встроены в HTML-страницу,
см. `<script id="test-data">` в `/tests/{slug}`), но эндпоинты
самостоятельны и пригодятся, если понадобится, например, мобильное
приложение или свой скрипт для тестирования новых тестов.

| Метод | Путь                              | Что делает                                             |
|-------|-----------------------------------|---------------------------------------------------------|
| GET   | `/api/tests/{slug}`               | Отдаёт тест в "безопасном" виде (вопросы, без ответов)   |
| POST  | `/api/tests/{slug}/result`        | Принимает `{"answers": {"q1":"a", ...}}`, отдаёт результат |
| GET   | `/shirt-image/{slug}/{resultID}`  | SVG-картинка футболки для конкретного результата         |
| GET   | `/healthz`                        | `{"status":"ok"}` — для проверок живости при деплое       |

Пример ручного вызова:

```bash
curl -X POST http://localhost:8080/api/tests/vibe-check/result \
  -H 'Content-Type: application/json' \
  -d '{"answers":{"q1":"a","q2":"b","q3":"a","q4":"a","q5":"a"}}'
```

## Известные упрощения (сознательно, для MVP)

- **Хранилище — JSON-файлы, а не база данных.** Достаточно для этапа
  проверки гипотезы; добавить новую реализацию `store.Store` (например,
  на Postgres) можно в любой момент, не трогая остальной код — см.
  комментарий в `internal/store/store.go`.
- **Нет авторизации и админки.** Тесты редактируются руками через git —
  ок, пока их немного и правит их один человек (Николай). Как только
  появится необходимость редактировать тесты без доступа к коду —
  это первое, что стоит добавить.
- **Картинка футболки — SVG-заглушка, а не реальный принт** (см. раздел
  выше про `internal/shirtimg`).
- **Нет персистентности результатов.** Сервер не запоминает, кто какой
  тест прошёл и какая футболка выпала — только считает и один раз
  показывает. Если понадобится, например, собирать статистику по
  результатам или дать пользователю ссылку на "мою футболку" — нужно
  будет добавить сохранение (лог в файл, база данных) в обработчик
  `POST /api/tests/{slug}/result`.
